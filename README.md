# VideoFetch HLS v2 public acceptance fixture

A small, permanent, public HLS source for acceptance-testing VideoFetch's
**muxed fMP4 clear-HLS** support over the real internet. It is test material
only: a synthetic colour test pattern with a 440 Hz tone. There is no real
media, no user data and nothing secret in this repository.

Submitted page: <https://papi299.github.io/videofetch-hls-v2-acceptance-fixture/>

## What it is for

It exercises one supported shape end to end: public DNS, HTTPS, CDN delivery,
VideoFetch analysis, playlist, map and fragment acquisition, FFmpeg/ffprobe
processing, upload and download delivery.

It does **not** demonstrate compatibility with arbitrary third-party HLS, other
CDNs or packagers, separate audio renditions, byte-range fMP4, general CMAF,
encrypted or DRM HLS, live HLS, discontinuities or alternate audio groups.

## Shape

```
index.html   HTML5 <video><source src="master.m3u8" type="application/x-mpegURL">
master.m3u8  one variant: 1920x1080, 25 fps, CODECS="avc1.640028,mp4a.40.2", no AUDIO group
media.m3u8   finite VOD fMP4 playlist (version 7, one URI-only EXT-X-MAP, 4 x 1 s fragments)
init.mp4     initialization segment (ftyp, moov)
seg-N.m4s    fragments (styp, sidx, moof, mdat), H.264 + AAC muxed in every fragment
```

The media playlist has no `EXT-X-KEY`, `EXT-X-BYTERANGE`, map `BYTERANGE`,
`EXT-X-DISCONTINUITY` or alternate audio.

## How it was made

The media and `media.m3u8` are the unmodified output of the positive `v2-fmp4`
recipe in VideoFetch's HLS-11 acceptance harness:
`generateHls11Rendition({ kind: "fmp4" })` in
[`deploy/acceptance/ytdlp-generic/fixtures/hls11-media.mjs`](https://github.com/Papi299/sail-lilac-comet-mint/blob/88f26318f5cf0434091ebd1e093e1017b1717f2f/deploy/acceptance/ytdlp-generic/fixtures/hls11-media.mjs)
at commit `88f26318f5cf0434091ebd1e093e1017b1717f2f`. They were generated by
FFmpeg `5.1.9-0+deb12u1` (Debian bookworm, `node:22-bookworm-slim` plus
`apt-get install ffmpeg`), with this command (`<dir>` is the output directory):

```
ffmpeg -hide_banner -nostdin -loglevel error -y -fflags +bitexact
  -f lavfi -i testsrc2=size=1920x1080:rate=25:duration=4
  -f lavfi -i sine=frequency=440:sample_rate=48000:duration=4
  -map 0:v -map 1:a
  -c:v libx264 -preset veryfast -threads 1 -pix_fmt yuv420p -profile:v high -level 4.0
  -g 25 -keyint_min 25 -sc_threshold 0 -b:v 600k -maxrate 600k -bufsize 600k -flags:v +bitexact
  -c:a aac -b:a 64k -ac 1 -flags:a +bitexact
  -map_metadata -1 -t 4
  -f hls -hls_time 1 -hls_playlist_type vod -hls_segment_type fmp4
  -hls_fmp4_init_filename init.mp4 -hls_flags independent_segments
  -hls_segment_filename <dir>/seg-%d.m4s <dir>/media.m3u8
```

The recipe is bit-exact: a second run produced identical bytes.

`master.m3u8` and `index.html` were written by hand to the same shape as that
harness's `hls11Master` and `hls11Page`. The harness-only `NAME` attribute and
`?sig=` query marker were left out, so nothing here needs a query string,
cookie or header. `BANDWIDTH=900000` is above the measured peak fragment rate
(829,368 bit/s). `avc1.640028` matches the `avcC` record in `init.mp4` (High
profile, level 4.0), and `mp4a.40.2` is AAC-LC.

## Integrity

`SHA256SUMS` lists every fixture file. Acceptance evidence binds to those
digests, so **do not modify these files**. A different fixture belongs in a new
directory or repository.
